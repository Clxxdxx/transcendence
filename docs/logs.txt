1. INTRODUCCIÓN Y ARQUITECTURA
================================================================================

La infraestructura ELK centraliza todos los logs del backend Laravel de
Transcendence: los persiste en Elasticsearch, los procesa mediante Logstash y
los visualiza en Kibana, accesible de forma segura a través de Nginx con
autenticación HTTP Basic.

STACK COMPLETO:
  - Elasticsearch 8.10.2  → motor de búsqueda y almacenamiento
  - Logstash 8.10.2       → pipeline de ingesta y transformación
  - Kibana 8.10.2         → visualización en https://localhost/kibana/
  - Nginx (alpine)        → reverse-proxy SSL + auth_basic
  - Laravel 11 / Monolog  → generación de eventos estructurados

BENEFICIOS:
  ✓ Centralización: todos los logs en un solo lugar
  ✓ Búsqueda Lucene en tiempo real sobre cualquier campo
  ✓ Retención automática vía ILM (365 días configurados)
  ✓ Acceso protegido con usuario/contraseña (HTTP Basic Auth)
  ✓ Credenciales nunca en el repositorio (Docker Secrets + .gitignore)
  ✓ Un solo comando levanta todo: make

    - ES_JAVA_OPTS=-Xms1g -Xmx1g

    container_name: transcendence_kibana

    - SERVER_REWRITEBASEPATH=true
    - DATA_SEARCH_SESSIONS_ENABLED=false
    - NEWSFEED_ENABLED=false
    - TELEMETRY_ENABLED=false
    - XPACK_SECURITY_ENCRYPTIONKEY=<clave 32 chars>
    - XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY=<clave 32 chars>
    - XPACK_REPORTING_ENCRYPTIONKEY=<clave 32 chars>
    - healthcheck: curl + grep '"available"' cada 15s, start_period 120s, retries 20
    - NO expone puerto 5601 al host (solo Nginx tiene acceso)
    - depends_on: elasticsearch (condition: service_healthy)

  logstash:
    image: docker.elastic.co/logstash/logstash:8.10.2
    container_name: transcendence_logstash
    - volumen pipeline: ./infra/logging/logstash/pipeline:/usr/share/logstash/pipeline:ro
    - ELASTICSEARCH_HOST=elasticsearch:9200
    - puerto: 5000:5000 (TCP para Laravel)
    - depends_on: elasticsearch

  volumes:
    esdata: name: transcendence_esdata

  Nota sobre red: NO declara network como external. Se une a transcendence_net
  definida en docker-compose.yml raíz, que la crea como bridge.


3.1.2  infra/logging/logstash/pipeline/logstash.conf
──────────────────────────────────────────────────────
  input {
    tcp { port => 5000; codec => json_lines; type => "laravel" }
  }
  filter {
    if [type] == "laravel" {
      date { ... }        # normaliza @timestamp desde datetime del JSON
      mutate {
        add_field => { "service" => "backend" }
      }
    }
  }
  output {
    elasticsearch {
      hosts => ["http://elasticsearch:9200"]
      index => "laravel-logs-write"   # alias gestionado por ILM
    }
  }

  - HOT   : activo, recibe datos

  - COLD  : 90 días, almacenamiento barato

4. SEGURIDAD: AUTENTICACIÓN NGINX + DOCKER SECRETS
================================================================================

FLUJO DE CREDENCIALES:
  1. Al ejecutar `make`, si no existe secrets/kibana_htpasswd, se solicita
     usuario y contraseña en la terminal de forma interactiva.
  2. Se genera el fichero htpasswd usando la imagen httpd:alpine (sin instalar
     nada en el host).
  3. El fichero se monta en Nginx como Docker Secret en /run/secrets/kibana_htpasswd
  4. Nginx sirve /kibana con auth_basic apuntando a ese fichero.
  5. Al hacer `make down` o `make clean` el fichero se borra automáticamente.

VENTAJAS DE ESTE ENFOQUE:
  ✓ Las credenciales nunca están en el repo (secrets/ en .gitignore)
  ✓ No se pasan como variables de entorno (no visibles en `docker inspect`)
  ✓ Se montan en /run/secrets/ (ruta estándar de Docker Secrets)
  ✓ Se regeneran en cada `make` (rotación natural)

NOTA SOBRE CACHÉ DEL NAVEGADOR:
  HTTP Basic Auth es recordada por el navegador mientras la sesión esté abierta.
  En visitas posteriores el navegador envía las credenciales automáticamente
  sin volver a preguntar. Esto es comportamiento estándar, no un fallo.
  Para forzar el diálogo de credenciales: usar ventana de incógnito.

5. CICLO DE VIDA: make → down → make DE NUEVO
================================================================================

Primera ejecución:
  $ make
  1. Pide usuario y contraseña para Kibana → genera secrets/kibana_htpasswd
  2. Levanta todos los contenedores (docker compose --wait)
     - Espera healthcheck de elasticsearch (hasta ~360s: 60s start + 15s×20)
     - Espera healthcheck de kibana (hasta ~420s: 120s start + 15s×20)
       comprueba que /kibana/api/status devuelve "available"
  3. Ejecuta migraciones Laravel
  4. Ejecuta logs-init:
     - Crea ILM policy en Elasticsearch
     - Sube index template
     - Crea índice laravel-logs-000001 con alias
     - Crea patrón de índice en Kibana

Parada:
  $ make down
  - Para todos los contenedores
  - Borra secrets/kibana_htpasswd  ← credenciales eliminadas

Segunda ejecución (datos persistidos en volumen esdata):
  $ make
  1. Pide nuevamente usuario y contraseña (el fichero no existe)
  2. Levanta contenedores (datos de Elasticsearch recuperados del volumen)
  3. logs-init es idempotente: si el índice ya existe no lo recrea
  4. Kibana recupera el patrón de índice guardado en Elasticsearch

Limpieza total:
  $ make clean
  - Para contenedores, borra volúmenes (datos Elasticsearch incluidos)
  - Borra secrets/kibana_htpasswd
  - En el próximo make todo se inicializa desde cero

6. SCRIPT DE INICIALIZACIÓN: create_resources.sh
================================================================================

Ubicación: infra/logging/create_resources.sh
Ejecutado por: make logs-init (dentro del contenedor backend)

FLUJO:
  1. wait_for Elasticsearch (60 intentos × 2s = máx 2 min)
     Condición: curl al endpoint devuelve HTTP 200

  2. Crear ILM policy laravel-logs-policy
     PUT /_ilm/policy/laravel-logs-policy  (cuerpo desde ilm_policy.json)

  3. Subir index template laravel-logs-template
     PUT /_index_template/laravel-logs-template  (cuerpo desde index_template.json)

  4. Crear índice inicial laravel-logs-000001 (si no existe)
     PUT /laravel-logs-000001 con alias laravel-logs-write y config ILM

  5. wait_for Kibana (90 intentos × 2s = máx 3 min)
     Condición: curl /kibana/api/status | grep -q '"available"'
     (no basta con que responda 200; debe estar en estado "available")
     Nota: si --wait ya garantizó que Kibana es healthy, este loop termina
     en el primer intento.

  6. Crear patrón de índice en Kibana
     POST /kibana/api/saved_objects/index-pattern/laravel-logs-pattern
     { "attributes": { "title": "laravel-logs-*", "timeFieldName": "@timestamp" } }

  Nota: los pasos de Kibana tienen || true / break para no abortar si Kibana
  tarda más de lo esperado.

7. CONFIGURACIÓN DE KIBANA DETRÁS DE PROXY NGINX
================================================================================

PROBLEMA RAÍZ:
  Kibana genera URLs de recursos (JS/CSS) relativas al basepath. Sin configurar
  SERVER_BASEPATH, todos los assets apuntan a "/" y Nginx los sirve como
  Angular/Laravel en lugar de Kibana.

SOLUCIÓN:
  - SERVER_BASEPATH=/kibana        → Kibana prefija todas sus URLs con /kibana
  - SERVER_REWRITEBASEPATH=true    → Kibana acepta requests que llegan con /kibana

CLAVES DE CIFRADO FIJAS:
  Sin claves fijas, Kibana genera claves aleatorias en cada reinicio. Esto
  invalida las sesiones y rompe SearchSessionService, causando:
    - Error 500 en /kibana/internal/session/_find
    - "Internal Server Error" en la página de Discover
    - WARN "[plugins.security.config] Generating a random key..."

  Se configuran tres claves estáticas de 32 caracteres en el compose:
    XPACK_SECURITY_ENCRYPTIONKEY
    XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY
    XPACK_REPORTING_ENCRYPTIONKEY

SESSIONS DESACTIVADAS:
  DATA_SEARCH_SESSIONS_ENABLED=false
  Evita que Kibana intente almacenar sesiones de búsqueda en Elasticsearch,
  lo que requeriría configuración adicional de índices del sistema.

FORMATO DE VARIABLES DE ENTORNO EN DOCKER:
  Kibana lee variables de entorno con _ (guiones bajos), NO con puntos.
  Correcto:   DATA_SEARCH_SESSIONS_ENABLED=false
  Incorrecto: DATA.SEARCH.SESSIONS.ENABLED=false  ← ignorado silenciosamente

HEALTHCHECK DE KIBANA:
  test: curl -sf http://localhost:5601/kibana/api/status | grep -q '"available"'
  Esto garantiza que docker compose --wait no continúa hasta que Kibana esté
  realmente operativa (no solo que el proceso haya arrancado).

9. CÓMO VER LOS LOGS EN KIBANA
================================================================================

URL DE ACCESO: https://localhost/kibana/
  - Credenciales: las que se introdujeron al ejecutar `make`
  - El navegador puede recordarlas automáticamente en visitas siguientes
  - Para forzar el diálogo de login: usar ventana de incógnito

PASO 1 - DISCOVER
──────────────────
  1. Ir a https://localhost/kibana/app/discover
  2. Selector de data view (arriba izquierda): elegir "laravel-logs-*"
     Si no aparece, ir a Stack Management → Data Views → Create data view:
       Name: laravel-logs
       Index pattern: laravel-logs-*
       Timestamp field: @timestamp
  3. Ajustar el rango temporal (arriba derecha): "Last 1 hour" o "Today"

PASO 2 - FILTROS KQL ÚTILES
────────────────────────────
  Solo errores:
    level_name: "ERROR"

  Errores y warnings:
    level_name: "ERROR" or level_name: "WARNING"

  Intentos fallidos de login (posible fuerza bruta):
    message: "login.failed"

  Actividad de un usuario concreto:
    context.user_id: 5

  Eventos desde una IP:
    context.ip: "192.168.1.100"

  Recuperación de contraseñas:
    message: password.recovery*

  Excepciones no controladas:
    message: "exception.unhandled"

PASO 3 - VERIFICACIÓN DESDE TERMINAL
──────────────────────────────────────
  # Contar documentos en Elasticsearch:
  docker exec transcendence_elasticsearch \
    curl -s http://localhost:9200/laravel-logs-000001/_count

  # Generar log de prueba manualmente desde Laravel:
  docker exec transcendence_backend \
    php artisan tinker --execute="Log::info('test', ['ts' => now()]);"

  # Ver logs procesados por Logstash:
  docker logs -f transcendence_logstash 2>&1 | grep -v monitoring

  # Comprobar que Kibana está healthy:
  docker inspect transcendence_kibana --format='{{.State.Health.Status}}'

11. TROUBLESHOOTING CONOCIDO Y SOLUCIONES APLICADAS
================================================================================

PROBLEMA: Nginx falla al arrancar con "host not found in upstream kibana"
  CAUSA: Nginx resuelve DNS de upstream al arrancar; si Kibana aún no existe,
         falla con error fatal.
  SOLUCIÓN APLICADA:
    resolver 127.0.0.11 valid=30s;   ← DNS interno de Docker
    set $kibana_upstream http://kibana:5601;
    proxy_pass $kibana_upstream;
    Con esto la resolución es lazy (en cada request, no al arrancar).

PROBLEMA: Kibana muestra página en blanco
  CAUSA: Sin SERVER_BASEPATH, los assets JS/CSS apuntan a "/" y Nginx los
         enruta a Angular/Laravel en lugar de Kibana.
  SOLUCIÓN APLICADA:
    SERVER_BASEPATH=/kibana
    SERVER_REWRITEBASEPATH=true

PROBLEMA: Error 500 en /kibana/internal/session/_find + "Internal Server Error"
  CAUSA 1: Variables de entorno con puntos (DATA.SEARCH.SESSIONS.ENABLED) no
           son leídas por Kibana en Docker; deben usar guiones bajos.
  CAUSA 2: Sin claves de cifrado fijas, Kibana genera una nueva en cada
           reinicio, invalidando todas las sesiones guardadas.
  SOLUCIÓN APLICADA:
    DATA_SEARCH_SESSIONS_ENABLED=false        (guiones bajos, no puntos)
    XPACK_SECURITY_ENCRYPTIONKEY=<32 chars>
    XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY=<32 chars>
    XPACK_REPORTING_ENCRYPTIONKEY=<32 chars>

PROBLEMA: logs-init falla con "Waiting for Kibana... (attempt N/90)"
  CAUSA: docker compose --wait no bloqueaba en Kibana porque no tenía
         healthcheck configurado. El contenedor aparecía "running" pero
         Kibana tardaba 2-3 min más en estar operativa.
  SOLUCIÓN APLICADA:
    Añadido healthcheck a Kibana en docker-compose.prod.yml:
      test: curl -sf http://localhost:5601/kibana/api/status | grep -q '"available"'
      start_period: 120s
      interval: 15s
      retries: 20
    Ahora --wait espera a que Kibana sea healthy antes de continuar.

PROBLEMA: Elasticsearch healthcheck timeout en el primer arranque
  CAUSA: Elasticsearch tarda más de 150s en inicializarse en máquinas con
         poca RAM o disco lento.
  SOLUCIÓN APLICADA:
    start_period: 60s
    interval: 15s
    retries: 20   ← total wait máximo: 60 + (15×20) = 360s

PROBLEMA: Logstash "No config files found in /usr/share/logstash/pipeline"
  CAUSA: La ruta del volumen en docker-compose.prod.yml era relativa al
         directorio infra/logging/ en lugar de la raíz del proyecto.
  SOLUCIÓN APLICADA:
    ./infra/logging/logstash/pipeline:/usr/share/logstash/pipeline:ro
    (ruta relativa a la raíz del proyecto donde se lanza docker compose)

PROBLEMA: Canal logstash no existe en Laravel
  CAUSA: El archivo config/logging.php del proyecto no tenía definido el canal
         'logstash'; Laravel caía al canal por defecto (stack/single).
  SOLUCIÓN APLICADA:
    Añadido manualmente el canal en config/logging.php con SocketHandler
    apuntando a tcp://logstash:5000 y JsonFormatter.

PROBLEMA: Error 499 en /kibana/internal/bsearch?compress=true
  CAUSA: Código 499 es "client closed request" (no 502). El navegador cancelaba
         la petición de búsqueda antes de recibir respuesta porque Kibana
         tardaba con buffering activado en el proxy.
  SOLUCIÓN APLICADA:
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_set_header Accept-Encoding "";

PROBLEMA: make down + make pide credenciales pero Kibana no las pide en navegador
  CAUSA: Comportamiento normal de HTTP Basic Auth. El navegador recuerda las
         credenciales en memoria para el origen (https://localhost).
  NO ES UN PROBLEMA: La protección sigue activa. Para forzar el diálogo,
  usar ventana de incógnito o cerrar completamente el navegador.

PROBLEMA: Directorios duplicados kibana/, elasticsearch/, logstash/ en la raíz
  CAUSA: Residuos de una configuración anterior que usaba esos directorios raíz.
  SOLUCIÓN APLICADA: sudo rm -rf (requerido sudo por permisos de Docker UID 82)
  La estructura correcta es infra/logging/ para todo lo relacionado con ELK.
